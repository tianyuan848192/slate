# GPU 渲染机：上线方案

2026-10-15 上线。

## 1. 结构

```
turn Lambda ──每轮开工──▶ render-warm Lambda ──预热──┐
     │                                               ▼
     ▼                                   渲染 Runtime（AgentCore Instance 模式）
Harness 会话（Agent）                     每个任务一台 GPU 实例（长片每 3 章一台）
  slate-render / slate-qa ──调用接口──▶   server.py → 每个请求一个 worker.py
     │      ▲                              本机 Chrome（EGL 通道用显卡）+ ffmpeg
     └─场景包─┴────── S3（任务目录）◀────── 片段、缩略图；events/ 里的渲染用量
finish Lambda ──任务停下来──▶ 删除容量提供方会话（机器几秒内开始关机）
```

- **Agent 和做片手册都没变**：命令还是 `slate-render 03`、`slate-qa 03`，返回格式也和以前一样。
- **兜底**：渲染机调不通（开不出机器、超时、拒绝）时，命令自动退回原来的远程浏览器方式。设置 `SLATE_RENDERER=browser` 可以强制走原来的方式。
- **机型**：只允许 T4 的 g4dn.xlarge 和 A10G 的 g5.xlarge，两种都是 4 核 16 GB。可以用 `-c renderInstanceTypes=a,b` 改。
- **网络**：账号默认 VPC 的公有子网，实例自动拿到公网 IP，可以直接访问 ECR 和 S3。安全组不开任何入站规则。
- **镜像**：x86。部署时由 CodeBuild 构建，构建上下文变了才重新构建（`infra/lib/render-image.ts`、`backend/renderbuild.py`）。

## 2. 一次渲染

1. 会话里的命令先算每镜的内容指纹，内容没变的镜头直接复用。指纹现在也包含镜头引用的共用目录，比如 `../_shared/`，改了共用组件，用到它的镜头会重渲。
2. 把要渲染的镜头打包，放进任务目录的 `render/<指纹>.tgz`。包里有分镜、brief、这几镜的配音时间轴、场景目录、引用到的共用目录和用户上传文件，一般几到几十 KB。自检时还会带上片段。
3. 用 Harness 执行角色调用渲染 Runtime，会话号是 `slate-render-<任务>`，长片是 `-g<组>`。请求里带着会话的任务范围临时凭证。
4. 渲染机：
   - 用这份凭证向 STS 确认身份：必须是任务数据角色，会话名必须是 `t-<任务号>`，场景包也必须在这个任务的目录下；
   - 之后的 S3 读写都用这份凭证。渲染服务自己的角色没有数据桶权限；
   - 每个请求起一个工作进程，几镜同时渲染（每镜最多 4 段）。浏览器报出显卡错误的镜头，自动改用 CPU 软件绘制重渲；
   - 片段放回 `clips/<指纹>.mp4`，缩略图放到 `render/qa/`。
5. 渲染机往这个任务的 `events/` 写一条 `render_usage`（忙碌秒数、机型），由 events Lambda 记成"渲染"一项。会话没法拦下这条记录。
6. 会话里的命令把片段和缩略图取回本地，写好 `clips/NN.json` 和 `qa/NN.*`，后面的合成、看图照常进行。

## 3. 开机和关机

- **预热**：turn Lambda 每轮开工时异步调用 render-warm，先把这个任务的渲染机开起来。开机加拉镜像约 2 分钟，在 Agent 读资料、写稿的时间里完成。
- **关机**：任务停下来时（完成、失败、等确认分镜），finish 和 turn 会**删除容量提供方会话**，机器几秒内开始关机，计费随之停止。
  - 注意：Instance 模式有两层会话。"停止 Runtime 会话"只停掉机器上的渲染服务，机器还开着，要等空闲超时才关。这是上线当天实测发现的，已经改正。
- **兜底**：空闲 10 分钟会自动关机，最长开 8 小时。
- **删栈**：容量提供方删掉以后，要等渲染机的网卡全部释放（实例终止约 10 分钟），再删安全组。这一步由自定义资源负责等待。

## 4. 计费

- 新增"渲染"一项：渲染机每次渲染、自检的忙碌秒数 × 机型单价。单价是 EC2 按需价加 7.8% 的管理费：g4dn.xlarge 每小时 0.567 美元，g5.xlarge 每小时 1.084 美元。管理端的计费设置页可以改。
- 开机、预热和空闲的时间不算在用户头上，由比例覆盖。
- 比例从 1.5 改成 **1 美元 = 1.3 Credit**，只影响以后的新记录，已经记下的 Credit 不变。

## 5. 上线实测（2026-10-15，3 个 15 秒任务，渲染机都是 g4dn.xlarge）

| 任务 | 风格 | 用时 | 渲染 | 合计 |
|---|---|---|---|---|
| 天空为什么是蓝色 | 蜡笔儿童绘本（WebGL，Agent 自己选的） | 14.6 分钟 | 22 次，忙碌 308 秒，0.063 Credit | 2.35 Credit |
| 手机充电越来越慢 | 等距信息图（2D） | 16.1 分钟 | 19 次，忙碌 134 秒，0.027 Credit | 3.64 Credit |
| 玻璃保温杯 | 玻璃质感产品（WebGL 3D） | 39.4 分钟（Agent 调玻璃质感改了三十多轮） | 62 次，忙碌 977 秒，0.200 Credit | 6.24 Credit |

- **2D 场景**：每镜 7～12 秒，每帧 0.09～0.15 秒，比历史上同一风格（14～21 秒）快约 1.6 倍。自检每镜约 3～10 秒，历史约 24 秒。
- **WebGL 场景**：蜡笔绘本每帧约 0.3 秒，玻璃质感每帧 0.15～0.9 秒，都能正常迭代。以前在远程浏览器上，一个 6 秒片段要 8～15 分钟，还可能超时失败。
- **4 核机器的局限**：画面复杂、几镜同时渲染时 CPU 会吃满。测试时用 8 核的 g6.2xlarge，2D 场景每镜只要 6～7 秒。如果要更快，可以把机型换成 2xlarge。
- **整体用时**：模型写稿、写代码的时间占到整个任务的 60%～70%，渲染已经不是大头。

## 6. 文件

| 文件 | 内容 |
|---|---|
| `agent/render/` | 渲染机镜像：`Dockerfile`、`server.py`（HTTP 接口、凭证校验、记用量）、`worker.py`（渲染和自检）、`localbrowser.py`（本机 Chrome、EGL 通道、驱动库路径） |
| `agent/image/slate/remote.py` | 会话里调用渲染机：打包、调用、取回 |
| `agent/image/slate/render.py`、`qa.py` | 能用渲染机时交给渲染机，调不通时退回原来的方式 |
| `backend/renderbuild.py` | 部署时构建镜像、删栈时等网卡释放 |
| `backend/renderwarm.py` | 预热 |
| `backend/lib/common.py` | `render_session`、`warm_render`、`stop_render` |
| `backend/events.py`、`backend/lib/billing.py` | 渲染计费 |
| `infra/lib/slate-stack.ts` | 渲染机的全部资源 |
