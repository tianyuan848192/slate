# Skill 统一成"写作方法 + 画风"两个维度（2026-10-18）

## 〇、实现情况（以这一节为准，后面是当初的方案）

按方案 A 做了：一段参考视频反编译出两份草稿，分开审、分开发布。和原方案不一样的地方：

| 方案里写的 | 实际做法 | 为什么 |
|---|---|---|
| 内置的 11 种写作方法搬到 `agent/skills/write-<id>/` | **不搬**，还在 `core-director/genres/`，目录还是 `genres.json` | 不从原理上影响做片质量：做片 Agent 读到的手册、写法文件和路径一个字都不变 |
| 用 Amazon Transcribe 转写旁白 | 用 **TwelveLabs Pegasus 1.5**（Bedrock，`us.twelvelabs.pegasus-1-5-v1:0`）直接看视频 | Transcribe 只给文字；Pegasus 能听出语气语调、语速、配乐和段落结构，写作方法更完整。实测 34 秒的视频约 7.6 秒返回，逐句旁白和时间都对（Pegasus 1.2 的输出不可用） |
| 全站改名 | 用户能看到的地方改名（新建页、工作流、Skills 页、任务详情、管理端、报错文字）；**Agent 用的手册不改名** | 同上，不动做片逻辑。手册里只加了一句：对用户说话时用"写作方法""画风" |

### 记录和存放

- 生成的 Skill 共用一张表、一套版本流程。记录多了三个字段：
  - `kind`：`visual`（画风）或 `writing`（写作方法）。以前的记录没有这个字段，按画风算，不用迁移；
  - `owner`：现在都是 `platform`。以后开放给普通用户时写 `user:<sub>`，只有本人看得到（`styles.visible` 已经按它过滤）；
  - `pair`：同一段参考视频生成的另一种 Skill 的 id。
- id 前缀：画风 `film-<短名>`，写作方法 `write-<短名>`，一个英文短名两种共用。
- 文件：都在数据桶 `styles/<id>/v<n>/`，`skill/` 是 Skill 本身，`review/` 是验证材料。写作方法的 `skill/` 只有 `SKILL.md` 和 `traits.json`；`review/` 有原片分镜表、听旁白的结果、每轮试写和报告，管理端能逐个打开看。
- 建任务时，选中的生成写作方法复制进任务的 `input/writing/<id>/`，任务说明的 `genre` 是 `{id, name, guide: "input/writing/<id>/SKILL.md", group, generated: true}`。做片手册加了一条：`generated` 为真时按 `guide` 读，通用打法按 `group`（讲解或宣传）选。以后这个写作方法更新或下架，老任务照常能改。
- 内测发布时，写作方法的说明书也写进内容把关的语料，和画风一样。

### 反编译

- 一个生成任务同时产出两种（也可以只要一种）。步骤：看视频 → 听旁白 → 提炼要素 → 写说明书 → 写引擎和示范镜头 → 写写作方法 → 自检打分。只要一种时，另一种的步骤跳过。
- 写作方法这条线（手册 `core-stylegen` 的"写作方法"一节）：
  1. `slate-style listen`：会话把参考视频的位置交给 llm Lambda，Lambda 调 Pegasus 读数据桶里的视频（视频不经过会话和模型上下文），得到逐句旁白、语气语调、语速、屏上大字、说话人、配乐和段落结构。长视频每 150 秒一段分开听；
  2. Agent 对齐拆帧的切点，写原片分镜表（每镜多长、说了什么、语气、作用、镜头类型，加平均镜头时长、每秒字数、几秒进入主题等统计）；
  3. 按内置写作方法的格式写说明书和要素；
  4. `slate-style trial-writing`：另开一次干净的模型调用，只给通用打法和这份说明书，换一个新题材写剧本和分镜；再请评审对照原片分镜表，给结构、开场、节奏、口吻各打 1～5 分；
  5. `slate-style export-writing`：检查 frontmatter、必备章节（结构、开场、节奏、旁白、镜头、时长）、大小、网址，以及**说明书和原片旁白有没有连续 12 个字以上相同**（只学讲法，原片的文案不能带走），通过后发布一版。
- 管理员的修改意见按记录分开：在写作方法上写的意见，Agent 只改写作方法，画风不动。

### 计费

- 看视频按 Pegasus 的价格记账：每秒视频 $0.00049，输出每百万 token $7.5，乘 1.3 换成 Credit，记在发起生成的管理员账上（和这个任务的其他用量一起）。用量页的类型叫"看视频"。
- 以后普通用户自己生成 Skill 时，生成任务归在他名下，用量自然记在他的账上，不用改计费。

### 关于 3D 图片和普通图片的引用

- 3D 图片现在就是引用代码：任务里放的是程序化的 three.js 模型（`model.js`），Agent 原样复制进 `scenes/_shared/`，镜头页面 import 工厂函数再加进场景，零件动画写在 `render(t)` 里。渲染图只用来让 Agent 看清楚长什么样。
- 普通图片（照片、截图、Logo）：2026-10-18 起支持，见 `docs/image-refs-design.md`。每张图写一句描述，Agent 写代码时按画面算图片的大小、位置和出现的时间，渲染进对应的帧。
- 以后 3D 图片也用"反编译"的思路时，可以沿用这一套：记录加一种 `kind`，复用版本、内测和公开的流程。


## 一、当初的现状（2026-10-18 改动前）

| | 画风 | 写作方法 |
|---|---|---|
| 内置 | 44 个，每个一个 Skill 目录：`agent/skills/<id>/`（说明书、引擎、示范片），目录在 `catalog.json` | 11 种，**不是独立的 Skill**：说明是做片手册里的 `core-director/genres/<id>.md`，目录在 `genres.json`；另有讲解类、宣传类两份通用打法 |
| 管理员生成 | 能，反编译参考视频生成。记录在 `STYLES/<id>`，文件在数据桶 `styles/<id>/v<n>/`，有待验证、内测、公开、下架 | 不能 |
| 建任务时 | 生成的画风复制进任务的 `input/styles/<id>/`，以后风格更新或下架，老任务照常能改 | 任务说明里带内置说明的路径 `genre.guide` |
| 内容把关 | 内置的随镜像打包进防泄露语料；生成的在内测发布时写进 `styles/protected/` | 只有内置的，随做片手册打包 |
| 网页 | 新建页的风格选择、Skills 页的风格库、工作流的音画节点 | 新建页的"写法"下拉框、工作流的文字节点；Skills 页里只在风格详情里提一句"常搭配的写法" |

其余 Skill 是平台内部的手册和组件，不算第三个维度，也不给用户选：

- 手册：做片（core-director）、3D 建模（core-model3d）、风格创建（core-stylegen）、影片风格通用用法（film-kit）；
- 组件库：镜头模板（kit-shots）、动作（kit-motion）、3D 素材画法（kit-3d），任何画风都能配。

**反编译现在只看画面**：拆帧、找切点、量动作，写画风的说明书和引擎。视频里的声音只用来判断"有没有音轨"，旁白说了什么、怎么组织，都没有读。

## 二、目标

- 用户看到的 Skill 只有两类：**写作方法**（剧本怎么组织）和**画风**（画面长什么样），任意搭配。
- 两类在系统里地位一样：
  - 都是独立的 Skill 包；
  - 都有内置的和管理员生成的；
  - 都有版本和发布流程；
  - 建任务时都把当时那一版复制进任务。
- 管理员反编译一段参考视频，产出两份草稿：一份写作方法，一份画风。**分开审、分开发布**：一段视频可能画面好、讲法一般，也可能反过来。

## 三、要调整的地方

### 1. Skill 的分类和存放

- 写作方法也做成独立的 Skill 目录，比如 `agent/skills/write-<id>/SKILL.md`，格式和现在的写法说明一样：
  - 先想清楚的几件事、结构、开场、深度、按时长、旁白和配音、常用镜头、常搭配的画风、常见问题；
  - 内置的 11 种从 `core-director/genres/` 搬过来，内容不改。
- 两份通用打法（讲解类、宣传类）还放在做片手册里，作为写作方法的公共底子。
- 目录合成一份：每一项带 `kind`（`writing` / `visual`），前端和接口都按它分两类。
- 生成的 Skill 共用一套记录和文件布局，加 `kind` 字段：现在的 `lib/styles.py`、`admin_styles.py` 推广成两类都能管。已有的生成画风默认 `kind=visual`，不用迁移。

### 2. Agent 和做片手册

- 手册第 2 节"写法和风格"：
  - 写作方法的说明换成新路径；
  - 生成的写作方法放在任务的 `input/writing/<id>/SKILL.md`，任务说明里的 `genre.guide` 指过去，和生成的画风一样。
- 长片各章的会话照样拿到写作方法的路径。
- 服务端把需求分析里的"片子类型"改成用户选的写作方法时，要能认出生成的写作方法。
- 防泄露语料：生成的写作方法在内测发布时，也写进把关语料。

### 3. 反编译：同时产出写作方法

在现有"看画面"的基础上，加一条"听旁白"的线：

1. **拿到说了什么**：从参考视频抽出音轨，转成带时间戳的文字。建议用 Amazon Transcribe，支持中文，按分钟计费，费用很低。没有旁白的视频，就用看图模型读关键帧里的字幕和大字。
2. **和画面对齐**：用已有的切点把逐句文字切到各个镜头，得到一张"原片分镜表"：每镜多长、说了什么、屏上有什么字、属于哪种镜头。
3. **提炼成写作方法**：
   - 分几段，每段做什么；
   - 前 3 秒怎么抓人；
   - 平均镜头多长，语速每秒几个字；
   - 旁白的口吻和常用说法；
   - 常用哪些镜头类型；
   - 怎么收尾。

   按内置写作方法的格式写成说明书。
4. **自检**：
   - 冷启动试写：另开一次干净的模型调用，只给它这份说明，换一个新题材写剧本和分镜，按"结构、开场、节奏像不像"打分；
   - 防照搬：试写的剧本和原片旁白连续很多字相同就拦下。只学结构和讲法，原片的文案不能带走，和画风"只学画法、不带走角色和 logo"是同一条边界。
5. **一次参考视频的局限**：一段视频提炼出的写作方法偏窄。可以考虑允许多传 1～2 段同类视频，一起提炼。

管理端相应调整：

- 新建时选"生成哪几种"，默认两种都要；
- 验证页分两个标签：
  - 画风：现在的对比视频、示范镜头、试写；
  - 写作方法：原片转写、原片分镜表、提炼的结构、试写剧本和打分；
- 两种各自走待验证 → 内测 → 公开 → 下架，各自要求至少一支测试片；
- 生成步骤加上"转写旁白、提炼写作方法、试写剧本"。

### 4. 用户端

- **名称统一**：全站"写法 / 风格"改成"写作方法 / 画风"。涉及：
  - 新建页、工作流节点、Skills 页、任务详情、管理端；
  - Agent 给用户看的话；
  - 讲解稿。
- **Skills 页**分两个区：写作方法、画风，生成的和内置的放在一起，内测的标"内测"。
  - 写作方法的详情：结构示意、适合什么题材、常搭配的画风；
  - 画风的详情：常搭配的写作方法。
- **新建页和工作流文字节点**：写作方法下拉框里加入生成的，内测的只有管理员看得到。

### 5. 后端接口

- Skill 目录接口：一次返回两类，带 `kind`，生成的按"公开的所有人可见、内测的只有管理员可见"过滤。
- 建任务：写作方法也能选生成的。建任务时复制进任务；用内测版建的任务，记成这一版的测试片。
- 任务详情：写作方法的名称也要能显示生成的。

### 6. 文档

- `docs/skills.md`、`docs/style-creator-design.md`、讲解稿里的相关章节。

## 四、建议分三步做

| 步 | 做什么 | 用户能看到的变化 |
|---|---|---|
| 1 | 统一名称和分类：写作方法变成独立 Skill 目录（内置 11 种搬过去）、目录加 `kind`、Skills 页分两区、全站改名 | 名称变了，Skills 页多了写作方法区；做片效果不变 |
| 2 | 生成的写作方法能被选用：记录和文件布局推广到两类、复制进任务、内测和公开、把关语料 | 管理员能手工上传或编辑一份写作方法，走内测和公开 |
| 3 | 反编译产出写作方法：转写、对齐、提炼、试写、防照搬、管理端验证页 | 一段参考视频出两份草稿，分开审、分开发布 |

第 1 步不碰做片逻辑，风险最小；第 3 步是新能力，工作量最大。
